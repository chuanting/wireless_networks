接收窗口：接收方说了算

A 发送方

B 接收方

窗口为 0：停发

应用取走数据

seq=0 len=1000

seq=1000 len=1000

ack=1000 win=3000

ack=2000 win=2000

seq=2000 len=1000

seq=3000 len=1000

ack=3000 win=1000

ack=4000 win=0

ack=4000 win=4000

seq=4000 len=1000

① 接收窗口 win

B 在每个 ACK 里写：缓冲区还剩多少字节。例中 B 共 4000 字节，应用暂时不取。

② 发送方遵守

未确认的字节数 ≤ win。

③ win = 0

发送方停下。应用取走数据后，B 发窗口更新；发送方还会定时探测，以防更新丢失。

对照 2.3：HDLC 用 RNR / RR 做“停 / 走”；TCP 直接告诉对方还能收多少，更精细。

【3 分钟】 流量控制：接收方来不及处理，怎么让发送方慢下来？ TCP 的办法：接收方在每个 ACK 里，把自己缓冲区剩下的空间，写进 win 字段，叫接收窗口。发送方必须遵守：未被确认的字节数，不能超过 win。 看图：B 的缓冲区 4000 字节，应用程序还没有来取数据。A 发了两段 seq = 0 和 seq = 1000，B 收到后，缓冲区里有了 1000，回 ack = 1000，win = 3000；再收到一段，回 ack = 2000，win = 2000。A 看到 win，知道还能再发 2000，于是发 seq = 2000、3000。B 又收下两段：ack = 3000，win = 1000；ack = 4000，win = 0——缓冲区满了。A 看到 win = 0，停下（橙色标注）。 过了一会儿，应用程序把缓冲区里的数据取走了，B 发一个窗口更新：ack = 4000，win = 4000。A 恢复发送。 一个小细节：如果这个窗口更新丢了，A 会永远等下去，B 也在等 A 发数据——死锁。所以 A 在窗口为 0 的时候，会定时发一个很小的“探测”报文，催对方回复当前的窗口。 对照 2.3：HDLC 用 RNR 和 RR，一个“停”一个“走”，是开关式的；TCP 用一个数值，直接告诉对方“我还能收多少”，更精细。 [提示：这里是流量控制——保护接收方；第 6 章还会讲“拥塞控制”——保护网络。两者不同。]
