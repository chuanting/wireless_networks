字节序号与累积确认

一个字节流被切成报文段（每段 1000 字节）

字节 1000–1999

字节 2000–2999

字节 3000–3999

字节 4000–4999

第 3 段在网络里丢了（灰色）；其余三段到达。

A 发 seq = 1000

数据 1000 字节 → B 回 ack = 2000（2000 之前都收到了）

A 发 seq = 2000

数据 1000 字节 → B 回 ack = 3000

A 发 seq = 4000

第 3 段没到，B 只能再回 ack = 3000（还是想要 3000）

seq：这一段第一个字节的编号

ack：我期待收到的下一个字节编号（累积确认）。

为什么按字节、不按段编号？

段的大小可以变；重传时可以重新分段、合并。

编号会不会用完？

32 位 = 2 的 32 次方 ≈ 43 亿字节。1 Gb/s 下约 34 秒就绕一圈。

和 2.2 一样：窗口必须远小于编号空间（≤ 一半），否则新旧分不清；高速下靠“时间戳”选项帮忙。

【4 分钟 · 重点】 TCP 怎样编号？和 HDLC 不一样：HDLC 对“帧”编号，3 位；TCP 对“字节”编号，32 位。 图里：一个数据流被切成每段 1000 字节的报文段。第 1 段装的是第 1000 到 1999 号字节，所以它的序号 seq 等于 1000——也就是这一段第一个字节的编号。 确认号 ack 的含义：我期待收到的下一个字节的编号，而且是“累积”的：ack = 2000 的意思是，2000 之前的所有字节我都收到了，现在想要 2000。 走一遍：A 发 seq = 1000，1000 个字节；B 回 ack = 2000。A 发 seq = 2000；B 回 ack = 3000。现在第 3 段（3000 到 3999）在网络里丢了。A 又发了 seq = 4000 的一段，它到了，但是 B 只能回 ack = 3000——因为 B 还是在等 3000 号字节。这就是“累积确认”：只确认到连续收到的最后一个。注意这一点——它是后面“快速重传”的基础。 为什么按字节编号，而不是按报文段编号？因为报文段的大小可以变：重传时，可以把几个小段合并成一个大段重新发。 编号会不会用完？32 位，2 的 32 次方约 43 亿字节。在 1 Gb/s 的链路上，每秒 1.25 亿字节，43 亿字节只要 34 秒就绕一圈回来。这和 2.2 里讲的“序号空间”问题是同一类：窗口必须远小于编号空间，否则分不清新旧。高速链路上靠“时间戳”选项来解决。 [验算：2^32 = 4 294 967 296 字节；÷ 1.25×10^8 字节/秒 ≈ 34.4 秒。]
