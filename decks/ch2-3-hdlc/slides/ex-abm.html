看 B 发的 I(0,1)：SN = 0：这是 B 的第 0 号数据；RN = 1：顺便告诉 A，“你的 0 号我收到了”。

看 A 发的 I(2,1)：SN = 2：A 的第 2 号数据；RN = 1：已收到 B 的 0 号，期望 1 号。

最后各发一个 RR：双方都没有新数据要发了，就用 RR 补上最后的确认：RR(3) 确认 A 的 0–2，RR(2) 确认 B 的 0–1。

中间没有一个单独的确认帧：确认都搭了数据帧的便车，链路用得更充分。

【4 分钟 · 重点】 第二个场景：全双工、平衡模式下，双方同时发数据，确认顺路带着。 时间 0 和 1：A 连续发 I(0,0)、I(1,0)。 时间 2：B 收到了 A 的 0 号帧，所以 B 自己的 RN = 1。这时 B 恰好有数据要发，就发 I(0,1)：SN = 0，是 B 自己的第 0 号数据；RN = 1，顺便告诉 A：“你的 0 号我收到了。”——这就是捎带确认。 时间 4：A 收到了 B 的第 0 号帧，A 的 RN = 1；这时 A 发出第 3 个数据帧 I(2,1)：SN = 2，RN = 1。同时，B 收到了 A 的 0 和 1 两帧，B 的 RN = 2，所以 B 发 I(1,2)：SN = 1，RN = 2。 时间 6：双方都没有新数据要发了，用 RR 补上最后的确认：B 收到了 A 的 2 号，发 RR(3)，意思是 A 的 0 到 2 号都收到了；A 收到了 B 的 1 号，发 RR(2)，意思是 B 的 0 和 1 号都收到了。 注意中间没有一个单独的确认帧：确认都搭了数据帧的便车。这就是全双工平衡模式效率高的原因。 [验算：每个帧的 RN 都等于“已经收到的对方帧数”，SN 从 0 起依次递增。]
