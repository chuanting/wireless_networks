第二部分 · ARQ 协议 · 停等式

为什么还要 RN？超时太短会出怪事

A 发送方

B 接收方

DATA SN=0

ACK RN=1

超时

DATA SN=0（重发）

DATA SN=1

ACK RN=1

经过

① 定时器设得太短：A 在 ACK 回到之前就超时，重发 SN=0。

② 第一个 ACK(RN=1) 到达，A 发 SN=1，这一帧在链路上丢了。

③ B 对重复的 SN=0 又回一个 ACK(RN=1)，此时才到达 A。

没有 RN 的 ACK

A 无法分辨“这是对哪一帧的确认”，会误以为 SN=1 已收到，直接发 SN=2。SN=1 永远丢失。

有 RN 就没事

A 要求 RN > SN 才算新的确认。这里 RN=1 不大于 SN=1，忽略；超时后重发 SN=1。

【3 分钟 · 可略（较难）】 再看一个更隐蔽的问题：如果定时器设得太短，会怎样？ 图：A 发 SN = 0；B 收到，回 ACK（RN = 1），但这个 ACK 路上比较慢；A 的定时器太短，在 ACK 回来之前就超时了，重发 SN = 0（橙色）。 接着，第一个 ACK(RN = 1) 到达，A 以为 SN = 0 被确认了，发下一帧 SN = 1；这一帧在链路上丢了（红叉）。 与此同时，B 收到了那个重复的 SN = 0，丢弃，但仍然回了一个 ACK(RN = 1)，这个 ACK 此时才到达 A。 如果 ACK 里没有 RN：A 看到一个 ACK，只能以为它是对刚发出的 SN = 1 的确认，于是发 SN = 2。结果：SN = 1 永远丢了！ 如果 ACK 里有 RN：A 的规则是，只有收到 RN 大于自己的 SN 的确认才算有效。现在 A 的 SN = 1，这个 ACK 的 RN = 1，不大于 SN，所以忽略。A 超时后重发 SN = 1，一切正常。 所以：SN 保证 B 不重复交付；RN 保证 A 不会被迟到的旧确认骗了。这就是等待式 ARQ 要求双向都带序号的原因。 [提示：这一页较难，时间紧可以只讲结论：“序号不是可有可无的，SN 防重复，RN 防误确认”。]
