把规则写完整：停等式 ARQ 的算法

A（发送方）

①

置 SN = 0

②

从上层取一个分组，编号 SN；没有就等

③

把带 SN 的帧发给 B，启动定时器

④

收到 B 的帧，若 RN 大于 SN：SN 加 1，回到 ②；超时仍没有：回到 ③ 重发

B（接收方）

①

置 RN = 0

②

每收到一个正确的帧：若 SN = RN，交给上层，RN 加 1；否则（重复帧）丢弃

③

无论是不是新帧，都在有限时间内把当前的 RN 放进一个帧，发回给 A

为什么对：B 只交付 SN = RN 的帧，交付一次 RN 就加 1，旧帧的 SN 一定小于 RN，不可能再被交付（不重复、不乱序）。只要每次传输成功的概率大于 0，重发有限次后，帧一定能到，ACK 也一定能回来（不会卡死）。

要求 RN 大于 SN 才算新的确认，是为了防止迟到的 ACK 被误认。

【3 分钟】 把规则写完整。A：置 SN = 0；从上层取一个分组，编号 SN，没有就等；把带 SN 的帧发给 B，启动定时器；收到 B 的帧，若 RN 大于 SN，SN 加 1，回到第二步；超时仍没有，回到第三步重发。B：置 RN = 0；每收到一个正确的帧，若 SN = RN，把分组交给上层，RN 加 1；否则（重复帧）直接丢弃；无论是不是新帧，都在有限的时间内把当前的 RN 放进一个帧里，发回给 A。 为什么这个协议是对的？一，不重复、不乱序：B 只交付 SN = RN 的帧，交付一次 RN 就加 1，旧帧的 SN 一定小于 RN，不可能再被交付。二，不会卡死：只要每次传输成功的概率大于 0，重发有限次后，帧一定能到，ACK 也一定能回来。 为什么要求 RN 大于 SN 才算新的确认？设想定时器设得太短：A 在 ACK 回到之前就超时，重发 SN=0；第一个 ACK(RN=1) 到达，A 发 SN=1，这一帧在链路上丢了；B 对重复的 SN=0 又回一个 ACK(RN=1)，此时才到达 A。如果 ACK 里没有 RN，A 无法分辨“这是对哪一帧的确认”，会误以为 SN=1 已收到，直接发 SN=2，SN=1 永远丢失。有 RN 就没事：A 要求 RN 大于 SN 才算新的确认，这里 RN = 1 不大于 SN = 1，忽略，超时后重发 SN = 1。
